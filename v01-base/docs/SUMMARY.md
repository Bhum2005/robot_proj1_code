# สรุปงานเว็บทั้งหมด — ข้อดี ข้อเสีย อาการที่เจอ

ไฟล์นี้เขียนไว้ให้อ่านก่อนแก้โค้ดต่อ (รวมถึง session ใหม่ของ Claude)
เนื้อหาคือเฉพาะส่วนเว็บ ไม่รวมเรื่องเฟิร์มแวร์ ESP32 กับการอ่านมิเตอร์ด้วย Hailo

## 1. สิ่งที่ทำเสร็จแล้ว

### 1.1 หน้าคุมหุ่น — `pi/server.py`
รันบน Raspberry Pi 5 พอร์ต 9000

- ภาพสดจากกล้องแบบ MJPEG ปรับขนาด/คุณภาพ/เฟรมเรตได้จากคอมมานด์ไลน์
- บังคับหุ่นด้วยจอย (evdev) และด้วยปุ่มบนหน้าเว็บ ส่งคำสั่งออก USB serial ไป ESP32-S3
- ปุ่มชัตเตอร์ถ่ายรูปมิเตอร์ความละเอียดเต็ม (`switch_mode_and_capture_file`) ภาพสดไม่ต้องจ่ายค่าภาพใหญ่
- ถ่ายแล้วขึ้นกล่องให้ใส่ **เลขห้อง + ประเภท (น้ำ/ไฟ/อื่น ๆ)** แล้วกดบันทึก — ได้ทั้งถ่ายจากหน้าเว็บและจากจอย
- ทุกรูปมีไฟล์ `.json` คู่กัน เก็บห้อง ประเภท เวลา และที่มา (จอย/เว็บ)
- `/tag` ติดป้ายรูปที่ถ่ายไปแล้วย้อนหลังได้ โดยเวลาถ่ายเดิมไม่เปลี่ยน
- `/status` บอกสุขภาพจริง: `lagMs` `dropHz` `kbps` จำนวนสายที่ต่ออยู่ — ใช้หาสาเหตุแล็คได้จริง
- ปุ่มกลับไปหน้าเจ้าของหอ (`--back-url`)

**ข้อดี** ไฟล์เดียว ไม่พึ่ง framework ย้ายเครื่องแค่คัดลอกไฟล์ ภาพสดวิ่งเร็วที่สุดเท่าที่สายไหว
**ข้อเสีย** ไฟล์ยาวมาก (3800+ บรรทัด) หน้า HTML/JS ฝังอยู่ในสตริง Python — แก้ง่ายแต่พลาดเรื่อง escape ได้ง่าย (เคยพลาดจริง ดูข้อ 4.6)

### 1.2 ตัวส่งรูปขึ้นคลัง — `pi/push.py`
วนทุก 20 วิ ส่งรูปที่ยังไม่ได้ส่งขึ้น hub ทนเน็ตหลุด ส่งต่อได้จากจุดที่ค้าง

จำสถานะรูปเป็น `"ขนาดไฟล์:เวลาแก้ไฟล์ json"` ถ้าไปติดป้ายห้องทีหลัง ค่าจะเปลี่ยน รูปจึงถูกส่งซ้ำพร้อมป้ายใหม่

**ข้อดี** Pi ดับ/เน็ตหลุดไม่เสียรูป
**ข้อเสีย** หน่วงได้ถึง 20 วิ และรูปอยู่สองที่ (Pi + hub) กินพื้นที่สองเท่า ยังไม่มีตัวลบรูปเก่าบน Pi

### 1.3 คลังกลาง — `hub/hub.py` + `hub/pages.py`
รันบนเครื่องที่เปิดตลอด พอร์ต 8080 นี่คือหัวใจของ "Pi ดับก็ยังเข้าเว็บได้"

สามหน้าในตัวเดียว:

| หน้า | ทางเข้า | ใครเข้า |
|---|---|---|
| เว็บลูกบ้าน | `/` | ลูกบ้าน — เลขห้อง + รหัส เห็นแค่ห้องตัวเอง |
| เว็บเจ้าของหอ | `{--owner-path}` (ตั้งเป็นทางลับได้) | เจ้าของหอ — เห็นทุกห้อง จัดการห้อง/รหัส |
| หน้าคุมหุ่น | ปุ่ม "คุมหุ่น" ในหน้าเจ้าของหอ เปิดซ้อนเต็มจอ (iframe) ลิงก์ไม่เปลี่ยน ส่งต่อไป Pi | เจ้าของหอ ที่ล็อกอินแล้วเท่านั้น |

- รหัสเก็บเป็นแฮช PBKDF2-HMAC-SHA256 200,000 รอบ ไม่เก็บรหัสจริง
- คุกกี้เซ็นด้วย HMAC จากกุญแจใน `secret.key` ปลอมไม่ได้
- กันเดารหัส: นับครั้งผิดต่อ IP แล้วล็อกนานขึ้นเรื่อย ๆ
- คำนวณหน่วยที่ใช้ให้เอง (เลขครั้งนี้ − เลขครั้งก่อน) แยกน้ำ/ไฟ
- รูปที่ยังไม่รู้ห้องไปอยู่ `_inbox` เจ้าของหอมาจัดเข้าห้องทีหลังได้
- ส่งต่อภาพสดจาก Pi ให้คนที่อยู่คนละเครือข่าย (ใช้คู่กับ Tailscale)

**ข้อดี** ไม่มีฐานข้อมูล ไม่มี dependency นอก Python มาตรฐาน รูปเรียงอยู่ในโฟลเดอร์ห้องตรง ๆ โปรแกรมพังรูปก็ยังเปิดดูได้ สำรอง = คัดลอกโฟลเดอร์เดียว
**ข้อเสีย** ยังเป็น HTTP ไม่ใช่ HTTPS (รหัสวิ่งเป็นข้อความธรรมดาถ้าไม่ผ่าน Tailscale) ไม่มีระบบรีเซ็ตรหัสเอง — ลูกบ้านลืมรหัสต้องให้เจ้าของหอตั้งใหม่ ไม่ได้ออกแบบให้รับคนเข้าพร้อมกันหลายสิบคน

### 1.4 คู่มือ + ชุดทดสอบ
- `docs/install.html` — ติดตั้งตั้งแต่ศูนย์ แยกตามเครื่อง มีปุ่มคัดลอกคำสั่ง
- `tests/regress.py` 15 ข้อ — **เส้นทางที่เคยพังจริงทั้งหมด** ไม่ใช่เคสที่คิดขึ้นเอง
- `tests/hubtest.py` 37 ข้อ — สิทธิ์การเข้าถึง การคำนวณหน่วย การแยกข้อมูลระหว่างห้อง
- `tests/stub/` — กล้อง/จอย/เซอร์เรียลจำลอง ทดสอบได้บนเครื่องที่ไม่มีหุ่น

ชุดทดสอบนี้เกิดขึ้นเพราะส่งโค้ดที่มีบั๊กไปหลายรอบ **แก้โค้ดแล้วให้รันทั้งสองชุดก่อนส่งทุกครั้ง**

## 2. การตัดสินใจเรื่องโครงสร้าง — ทำไมเลือกแบบนี้

### 2.1 ทำไมแยก hub ออกจาก Pi
ตอนแรกทุกอย่างอยู่บน Pi แต่โจทย์คือ "Pi ดับก็ต้องดูรูปได้" ซึ่งทำไม่ได้ถ้าไฟล์อยู่บน Pi เท่านั้น
จึงให้ Pi เป็นแค่คนถ่ายและส่งออก ส่วนคลังอยู่เครื่องที่เปิดตลอด

**แลกกับ** ต้องดูแลสองเครื่อง และมีค่าสองตัวที่ต้องตรงกันข้ามเครื่อง (โทเคน, รหัสหน้าคุมหุ่น) — พลาดบ่อยที่สุดในการติดตั้ง

### 2.2 ทำไมไม่ใช้ Render / Cloudflare Tunnel
ลองประเมินทั้งคู่แล้ว ไม่เหมาะ

- **Render ฟรี** ไม่มีดิสก์ถาวร รูปหายทุกครั้งที่ deploy และหลับหลังไม่มีคนใช้ 15 นาที
- **Cloudflare quick tunnel** URL เปลี่ยนทุกครั้งที่รีสตาร์ท ต้องแจกลิงก์ใหม่ทุกครั้ง ถ้าจะให้ URL อยู่นิ่งต้องมีโดเมน = เสียเงิน
- **Cloudflare + โดเมน** ใช้ได้ดี แต่ต้องจ่ายค่าโดเมน (ไม่เอา)

สรุปเลือก **Tailscale** — ฟรี ทุกเครื่องได้ IP `100.x.x.x` ที่ไม่เปลี่ยนไม่ว่าจะย้ายเครือข่าย ต่อตรงเครื่องถึงเครื่อง เข้ารหัสให้
ถ้าจะให้คนนอก (ลูกบ้าน) เข้าได้โดยไม่ต้องลง Tailscale ใช้ **Tailscale Funnel** ฟรีทุกแพ็กเกจ

**ข้อเสียของ Tailscale** ลูกบ้านต้องลงแอปด้วย (ถ้าไม่ใช้ Funnel) และถ้าเน็ตเป็น hotspot มือถือ การต่อบางครั้งจะกลายเป็น `relay` ซึ่งช้ากว่า `direct`

### 2.3 ทำไมไม่มีฐานข้อมูล
เพราะงานนี้ของอยู่เป็นรูป ไม่ใช่ตาราง และสำคัญกว่าคือ **ถ้าโปรแกรมพังในอนาคต ข้อมูลต้องไม่ติดอยู่ในฐานข้อมูลที่เปิดไม่ได้**
ตอนนี้รูปอยู่ที่ `photos/<ห้อง>/<ปี-เดือน>/` เปิดด้วยโปรแกรมดูรูปธรรมดาได้เลย

**แลกกับ** ค้นหาข้ามห้องช้าถ้ารูปเยอะหลายหมื่น และแก้ข้อมูลพร้อมกันสองเครื่องได้ไม่ดี

### 2.4 ทำไมหน้าคุมหุ่นถูกส่งต่อ (proxy) ผ่าน hub ไม่ใช่เข้า Pi ตรง
เพราะต้องการให้ล็อกอินที่เดียว และเข้าได้จากที่ไหนก็ได้ โดย Pi ไม่ต้องเปิดออกเน็ต
วัดแล้ว overhead ของการส่งต่ออยู่ที่ประมาณ **2 ms** (82 ms ผ่าน proxy vs 84 ms เข้าตรง) ไม่ใช่สาเหตุแล็ค

## 3. อาการแล็คและภาพค้าง — เรื่องนี้ใช้เวลามากที่สุด

อาการที่เห็นคือ "ขึ้นภาพค้าง กำลังต่อใหม่ สายหลุด" และบางทีค้างไปเลย
มันไม่ใช่สาเหตุเดียว แต่เป็น **4 สาเหตุซ้อนกัน** และกว่าจะแยกออกต้องวัดทีละชั้น

### สาเหตุที่ 1 — การเขียนแบบ blocking ในตัวส่งต่อไปรั้ง Pi
ตัวส่งต่อเดิมเป็นลูปเดียว: อ่านจาก Pi แล้วเขียนให้เบราว์เซอร์
ถ้าเบราว์เซอร์รับช้า การเขียนจะค้าง และระหว่างที่ค้างมันก็ **หยุดอ่านจาก Pi** ด้วย
ผลคือฝั่ง Pi เฟรมล้น `dropHz` ขึ้นไป 12 และ `lagMs` ขึ้นไปถึง **424,000 ms** (เจ็ดนาที)

**แก้** แยกเป็นสองเธรด เธรดอ่านดูด Pi เต็มความเร็วตลอดเวลาแต่เก็บไว้แค่เฟรมล่าสุด เธรดเขียนส่งเฟรมล่าสุดเท่าที่สายไหว เฟรมที่เก่าแล้วทิ้งทิ้งไป
พร้อมกับตั้ง `SO_SNDBUF` เท่าขนาดหนึ่งเฟรมพอดี (บัฟเฟอร์ใหญ่เกิน = หน่วงเพิ่มเปล่า ๆ) และเปิด `TCP_NODELAY`

**บทเรียน** ในตัวส่งต่อภาพสด ของใหม่สำคัญกว่าของครบ ยอมทิ้งเฟรมดีกว่าส่งของเก่า

### สาเหตุที่ 2 — เลขความหน่วงหลอก เพราะโค้ดซ้ำสองที่
`lagMs` โตขึ้น 1 วินาทีต่อวินาทีทุกครั้งหลังกดถ่ายรูป ดูเหมือนภาพค้างจริง
สาเหตุจริงคือมีคลาส `StreamOut` อยู่ **สองชุด** ชุดที่ใช้ตอนรีสตาร์ทกล้องหลังถ่ายรูปลืมเซ็ต `frame_t`
เลขจึงหลอก และเลขหลอกนี้พาไปแก้ผิดทางสองรอบ

**แก้** รวมเป็นเมธอด `_output()` เดียว
**บทเรียน** โค้ดก๊อปสองที่จะแยกร่างกันเสมอ และ metric ที่ผิดแพงกว่าไม่มี metric

### สาเหตุที่ 3 — แท็บที่ไม่ได้ดูยังดูดภาพอยู่
เปิดหน้าคุมหุ่นค้างไว้หลายแท็บ ทุกแท็บยังดึงภาพสด แบนด์วิดท์ถูกแบ่ง
**แก้** หยุดสตรีมเมื่อแท็บถูกซ่อน และต่อใหม่เมื่อกลับมา (แต่ต้องซ่อนนานเกิน 4 วิ ไม่งั้นสลับแท็บเร็ว ๆ จะต่อใหม่รัว ๆ เอง)

### สาเหตุที่ 4 — แบนด์วิดท์ไม่พอจริง ๆ (ตัวจริง)
1280×720 คุณภาพ 75 ที่ 12 fps = ราว **3.3 Mbit/s** ซึ่งเกินที่ hotspot มือถือรับได้
เฟรมไปกองอยู่ใน driver WiFi ซึ่ง **Pi มองไม่เห็น** — ฝั่ง Pi ตัวเลขจึงสวยทุกตัวแต่ภาพยังตามหลัง

**แก้** ลดเป็น `--stream-size 854x480 --stream-quality 60` = ราว **1.1 Mbit/s**

**บทเรียน** ตัวเลขที่ต้นทางสวยไม่ได้แปลว่าไม่มีคอขวด คอขวดอาจอยู่ตรงที่ไม่มีใครวัด

### สาเหตุที่ 5 — MJPEG เป็นแบบ "ดัน" ซึ่งคุมคิวกลางทางไม่ได้ (แก้แล้ว)
อาการ "ยังค้างบ่อยแม้ต่อ Pi ตรง" มาจากตัว MJPEG เอง ไม่ใช่ hub
`/stream` ดันเฟรมออกไปเรื่อย ๆ ตามจังหวะกล้อง ถ้าทางไหนช้า (driver WiFi, hotspot) เฟรมจะไปกองตรงนั้น
`SO_SNDBUF` คุมได้แค่คิวบน Pi คิวที่อยู่ไกลออกไปคุมไม่ได้ ภาพจึงตามหลังจนยามเฝ้าตัดสายต่อใหม่

ดูจากตัวอย่าง `robot-update` ที่ไม่มีอาการนี้ ต่างกันตรงที่หน้าเว็บ **ขอภาพทีละใบ** (`/api/frame.jpg?after=<เลข>`)
แล้วขอใบถัดไปก็ต่อเมื่อใบก่อนขึ้นจอแล้ว ในท่อจึงมีภาพได้แค่ใบเดียว สายช้า = fps ลด แต่ภาพเป็นภาพล่าสุดเสมอ

**แก้** เพิ่ม `/frame?id=..&after=<เลข>` ใน `pi/server.py` (ส่งเฟรมล่าสุดที่ใหม่กว่า `after`, รอได้ 1.5 วิ, ไม่มีก็ตอบ 204)
หน้าคุมหุ่นเปลี่ยนจาก `<img src=/stream>` เป็นลูป `fetch` ทีละใบ หยุดดึงเองเมื่อแท็บถูกซ่อน
hub ส่งต่อหัว `X-Frame-Seq` ไปด้วย ยามเฝ้า (`txN`) ยังใช้ได้เหมือนเดิมเพราะนับทุกใบที่ส่งออก
`/stream` ยังอยู่ (หน้าทดสอบแล็คกับ regress ข้อ 1–4 ใช้อยู่)
ทดสอบใน `tests/regress.py` ข้อ 6 — คนดูช้าได้เลขเฟรมกระโดดข้ามใบเก่า ความหน่วงฝั่ง Pi ไม่โต

**บทเรียน** ภาพสดผ่านเน็ตที่ไม่แน่นอน ให้ปลายทางเป็นคนกำหนดจังหวะ (pull) ดีกว่าให้ต้นทางดัน (push)

### อาการที่ยังไม่ปิดเคส (ก่อนแก้สาเหตุที่ 5)
B รายงานว่า "ยังค้างอยู่บ่อย ๆ แม้ต่อ Pi ตรง" หลังติดตั้งเวอร์ชันลดขนาดภาพ แต่ยังไม่ได้ส่งค่า `kbps` จาก `/status` มา
**ขั้นต่อไปที่ต้องทำ** เปิดหน้าคุมหุ่น ปล่อยให้ค้าง แล้วเปิด `http://<pi>:9000/status` ดู `kbps` `dropHz` `lagMs` ตอนที่ค้างอยู่
- `kbps` ตกลงใกล้ 0 แต่ `dropHz` สูง = สายรับไม่ทัน ให้ลดเหลือ `640x360 quality 50`
- `lagMs` โตเรื่อย ๆ = ฝั่ง Pi เอง กลับไปดูเส้นทางรีสตาร์ทกล้อง
- ตัวเลขทุกตัวปกติแต่ภาพค้าง = ปัญหาอยู่ที่ WiFi/driver ไม่ใช่โค้ด

## 5. ข้อเสียรวมของระบบที่ยังอยู่ (ควรรู้ก่อนใช้จริง)

1. **ยังเป็น HTTP** ถ้าไม่ผ่าน Tailscale รหัสลูกบ้านวิ่งเป็นข้อความธรรมดา — ถ้าจะใช้จริงนอกเดโม ต้องใส่ HTTPS (Tailscale Funnel ให้มาในตัว)
2. **รหัสเดโมอ่อน** (`admin12345678`) ตั้งใจให้ง่ายเพราะเป็นงานส่ง ถ้าใช้จริงต้องเปลี่ยน
3. **ไม่มีการลบรูปเก่า** ทั้งบน Pi และบน hub พื้นที่จะโตเรื่อย ๆ
4. **ไม่มีรีเซ็ตรหัสเอง** ลูกบ้านลืมต้องให้เจ้าของหอตั้งใหม่
5. **เครื่องที่เปิดตลอดเป็นจุดเดียวที่พังไม่ได้** ถ้าโน้ตบุ๊กดับ เว็บลูกบ้านล่มด้วย (รูปไม่หาย แต่เข้าไม่ได้)
6. **ยังอ่านเลขมิเตอร์เองไม่ได้** ต้องคนพิมพ์ — ส่วน Hailo พักไว้
7. **หน้าเว็บฝังใน Python** แก้หน้าตาต้องแก้สตริงใน `pages.py` เสี่ยงเรื่อง escape
8. **ไม่ได้ทดสอบกับคนใช้พร้อมกันหลายคน** ทดสอบมากสุดคือไม่กี่สาย

## 6. สิ่งที่ยังไม่เสร็จ (เรียงตามความสำคัญ)

1. **ลองโหมดขอทีละใบบนหุ่นจริง** (สาเหตุที่ 5) — ถ้ายังค้าง ให้เก็บค่า `kbps` `dropHz` `lagMs` ตอนที่ค้างตามวิธีในข้อ 3 แล้วพิจารณาเปลี่ยนภาพนิ่งเป็นสตรีมคู่ main+lores แบบ `robot-update` (ไม่ต้องสลับโหมดกล้องตอนกดถ่าย ภาพไม่หยุด 1–3 วิ)
2. **แฟลชเฟิร์มแวร์ ESP32 v9** (`esp32/main.cpp`) — เพิ่มคำสั่ง `X` แล้ว (ล้อหยุดทันทีไม่ผ่าน ramp + แปรงดับ + แขนค้าง) และดับแปรงเองถ้าไม่ได้ `#M` จาก Pi เกิน 2 วิ เหลือแฟลชลงบอร์ดแล้วเช็คว่าส่ง `?` แล้วตอบ `fw v9`
3. **เปิด HTTPS** ด้วย Tailscale Funnel ถ้าจะให้ลูกบ้านเข้าจริง
4. **ตัวลบรูปเก่าอัตโนมัติ** เช่นเก็บบน Pi แค่ 7 วันหลังส่งขึ้น hub สำเร็จ
5. **อ่านเลขมิเตอร์อัตโนมัติด้วย Hailo** — พักไว้ รอคลิปวิดีโอจากกล้องบนหุ่นมาเทรน
6. **ย้าย hub ขึ้นเครื่องที่เปิดตลอดจริง ๆ** (VPS ถูก ๆ หรือ Pi อีกตัว) ไม่ใช่โน้ตบุ๊ก
