เทียบระบบภาพสดหุ่นมิเตอร์
PiVistation 5 + ESP32-S3 · หุ่นจดมิเตอร์หอพัก · 15 ต.ค. 2569

ภาพสดของหุ่น: สามระบบ เลือกทางไหน

เทียบระบบกล้องและภาพสดสามแบบ ได้แก่ ระบบเดิมของเรา, raspberry_pi (WebRTC + เว็บแคม Logitech) และ robot-update (PiVistation 5 ชุดเดียวกับเรา) โดยอ่านจากโค้ดจริงทุกบรรทัดที่เกี่ยวกับกล้อง การส่งภาพ และการขับ แล้ววัดผลเป็นตัวเลขในเครื่องทดสอบ

ข้อสรุป

ใช้ระบบของเราเป็นฐานต่อ แล้วเปิดวิดีโอ WebRTC แบบที่ raspberry_pi ใช้

ส่วนนี้เขียนเสร็จและผ่านการทดสอบในเครื่องจำลองแล้ว เหลือติดตั้งลงหุ่น ไม่ควรย้ายไปใช้ระบบของคนอื่นทั้งระบบ เพราะทั้งสองระบบจะทำให้เสียภาพนิ่ง 64MP การขับผ่านเว็บพร้อมจอย แขน pan และเว็บ hub ไป ส่วน robot-update มีของดีที่ควรยืมมาทีหลังสามอย่าง: AI แนะนำเลขมิเตอร์, ขั้นตอนบันทึกค่าแบบชนิด→ห้อง→ค่า, และการถ่ายภาพแบบไม่หยุดภาพสด

อุปกรณ์ที่ใช้จริง

ทั้งสามระบบต้องรันบนฮาร์ดแวร์ชุดนี้ ข้อจำกัดของฮาร์ดแวร์จึงเป็นตัวตัดสินหลายเรื่อง

สถาปัตยกรรมทั้งสี่แบบ

ทุกรูปวาดผังเดียวกัน: ซ้ายคืออุปกรณ์ กลางคือโปรแกรมบน Pi ขวาคือสิ่งที่อยู่นอก Pi เส้นประแนวตั้งคือจุดที่ข้อมูลออกจากเครื่องไปทางเครือข่าย กล่องส้มคือจุดอ่อน กล่องเขียวคือจุดที่ทำให้ลื่น วงกลมเลขอธิบายอยู่ใต้รูป

ก. ระบบเดิมของเรา (ตอนเริ่ม เช้า 15 ต.ค.)

  • 1เน็ตช้าเมื่อไหร่ เฟรมไปกองอยู่ในท่อที่ Pi มองไม่เห็น ภาพตามหลังความจริงหลายวินาที และถ้าแพ็กเก็ตหาย TCP ต้องหยุดรอส่งซ้ำ
  • 2http.server ส่งหัวกับเนื้อความแยกกัน (Nagle) วัดได้ว่าทุกคำขอโดนหน่วง 44 ms คงที่ บน Windows ถึง 200 ms และหน้าเว็บยิง /drive ทุก 120 ms กับ /status ทุก 250 ms โดยไม่รอคำตอบ คำขอจึงซ้อนกันจนเต็ม
  • 3ต้องหยุดสตรีมแล้วสลับเป็นโหมดภาพนิ่งเต็มเซนเซอร์ ภาพสดจึงค้าง 1–3 วินาทีทุกครั้งที่กดถ่าย

ข. raspberry_pi (WebRTC + เว็บแคม Logitech)

  • 1ใน zip ไม่มีไฟล์ตั้งค่า MediaMTX ส่วนนี้จึงอนุมานจากโค้ด: หน้าเว็บเปิด iframe ไปที่ :8889/robot และกล้องอ่านจาก CAMERA_RTSP_URL ได้ เว็บแคม Brio ส่ง H.264 เองไม่ได้ (มีแค่ MJPEG/YUY2/NV12) จึงต้องมีตัวแปลง เช่น ffmpeg ตามคู่มือ MediaMTX ถ้าเป็น Pi 5 ก็ต้องใช้ซีพียูแปลงเหมือนกัน
  • 2ภาพที่ถ่ายคือเฟรมจากวิดีโอที่ถูกบีบอัดแล้ว แล้วครอปตรงกลางเพื่อซูม ซูม 4× เหลือพิกเซลจริงแค่หนึ่งในสิบหก รูปที่อัปขึ้น Drive ถูกตั้งให้ใครมีลิงก์ก็เปิดได้
  • 3ESP32 ส่ง PI_CMD DRIVE มาให้ Pi แต่ Pi แค่ตรวจรูปแบบแล้วตอบ OK ไม่ได้สั่งมอเตอร์ และหน้าเว็บไม่มีปุ่มขับเลย ระบบนี้จึงไม่ได้ออกแบบมาให้ขับหุ่นผ่านภาพสด

ค. robot-update (PiVistation 5 ชุดเดียวกับเรา)

  • 1หน้าเว็บขอใบใหม่หลังใบเก่าขึ้นจอแล้ว วิธีนี้เหมือน /frame ที่เราเคยใช้ ภาพไม่สะสม แต่ทุกใบต้องรอรอบไปกลับหนึ่งรอบ ระบบนี้ดูลื่นบน hotspot เพราะภาพเล็กมาก (กว้าง 480 จาก 64MP) แลกกับรายละเอียด และเข้ารหัส JPEG ใหม่ทุกคำขอ ถ้ามีหลายคนดูก็เข้ารหัสซ้ำหลายรอบ
  • 2ไม่มีรหัสผ่านทั้งหน้าเว็บและ WebSocket ใครอยู่วงเดียวกันขับหุ่นได้ และพอร์ต 8765 แยกจากหน้าเว็บ ถ้าจะส่งต่อผ่าน hub หรือ Funnel ต้องเขียนเพิ่ม
  • 3คุยกับ ESP32 เป็น JSON (เดินหน้า/ถอย/ซ้าย/ขวาแบบเปิด-ปิด + tilt + blower) ใช้กับเฟิร์มแวร์ v9 ของเราไม่ได้ และไม่มีความเร็วอนาล็อก แขน pan หรือจอย

ง. ที่แนะนำ: ระบบเดิม + วิดีโอ WebRTC (เขียนเสร็จแล้ว)

  • 1ภาพนิ่ง 64MP ยังต้องสลับโหมด ภาพหยุด 1–3 วิเหมือนเดิม และวิดีโอต้องเปิดสายใหม่หลังถ่าย ระหว่างนั้นหน้าเว็บสลับไปใช้ JPEG ให้เองแล้วกลับมาเป็นวิดีโอเอง ถ้าจะเลี่ยง ทำปุ่ม 'ถ่ายเร็ว' จากสตรีมหลัก 1280×720 แบบที่ robot-update ทำได้ (ภาพเล็กกว่า แต่ไม่หยุด)

ตัวเลขที่วัดได้

สร้างคลิปทดสอบ 8 วินาที 25 fps จากภาพมิเตอร์จริงในชุดทดสอบของ robot-update วางบนผนังที่มีลวดลาย เติม noise แบบเซนเซอร์ แล้วเลื่อนภาพเหมือนหุ่นหมุนตัว จากนั้นเข้ารหัสด้วยค่าที่แต่ละระบบใช้ แล้ววัดว่าต้องใช้เน็ตเท่าไหร่ และภาพที่ได้เหมือนต้นฉบับแค่ไหน (SSIM ยิ่งใกล้ 1 ยิ่งเหมือน ทุกแบบถูกขยายกลับเป็น 1280×720 ก่อนเทียบ ภาพที่ย่อเล็กจึงเสียคะแนนตามรายละเอียดที่หายไปจริง)

ภาพที่ไปถึงผู้ใช้ ผ่านลิงก์จำลอง

ใช้ตัวจำลองลิงก์ (หน่วงเวลา + จำกัดความเร็ว) วิ่งกับ server.py จริงพร้อมกล้องจำลอง เฟรมละ 40 KB ทั้งสองแบบ แบบขอทีละใบเป็นกลไกเดียวกับที่ robot-update ใช้

ทำไมหุ่นอยู่ไกลแล้วภาพค้าง: เพดานของ TCP เมื่อแพ็กเก็ตหาย

TCP ลดความเร็วลงทุกครั้งที่แพ็กเก็ตหาย ตารางนี้ประมาณเพดานความเร็วด้วยสูตรของ Mathis (MSS 1448 ไบต์) เทียบกับที่ภาพสดต้องใช้ ถ้าเพดานต่ำกว่าที่ต้องใช้ ภาพจะค้างเป็นพัก ๆ ส่วน WebRTC ใช้ UDP จึงไม่มีเพดานแบบนี้ แพ็กเก็ตที่หายทำให้ภาพแตกแค่แวบเดียว และภาพจะคมกลับมาที่ภาพหลักถัดไป (ตั้งไว้ทุก 1 วินาที)

ข้อดีและข้อเสีย

ก. ระบบเดิมของเรา

ข้อดี

  • ภาพนิ่ง 64MP ซูมครอปที่เซนเซอร์ AF กรอบกลาง และสแกนหาจุดคม เหมาะกับการอ่านตัวเลขมิเตอร์ที่สุด
  • ขับอนาล็อกผ่านเว็บและจอย แขน pan/tilt เฟิร์มแวร์มีระบบหยุดเอง
  • มี hub: เว็บลูกบ้าน/เจ้าของหอ ส่งต่อหน้าคุมหุ่น เก็บรูปแม้ Pi ดับ
  • มีรหัสผ่าน และชุดทดสอบที่ไม่ต้องใช้หุ่นจริง

ข้อเสีย

  • ตอนเริ่ม: ภาพสดดันต่อเนื่องจนสะสม, หน่วง 40–200 ms ทุกคำขอ, คำขอซ้อนกัน (แก้แล้ววันนี้)
  • JPEG ใช้เน็ตมาก และวิ่งบน TCP: เน็ตแย่ = ค้าง
  • ถ่ายภาพนิ่งแล้วภาพหยุด 1–3 วิ
  • ไฟล์ server.py ใหญ่ (หน้าเว็บฝังอยู่ในโค้ด)

ข. raspberry_pi

ข้อดี

  • วิดีโอ WebRTC บน UDP: ใช้เน็ตน้อย ไม่ค้างเวลาแพ็กเก็ตหาย ตรงกับอาการตอนหุ่นอยู่ไกล
  • ใช้ MediaMTX สำเร็จรูป โค้ดเองน้อย
  • อัปโหลดอยู่ในเธรดแยก กดถ่ายแล้วไม่ต้องรอ

ข้อเสีย

  • ออกแบบมาสำหรับเว็บแคม USB ไม่ใช่กล้อง CSI 64MP
  • ภาพถ่ายมาจากวิดีโอที่ถูกบีบอัดแล้ว ซูมด้วยการครอป ความชัดน้อยกว่ามาก
  • ไม่มีการขับหุ่นผ่านเว็บ ไม่มีรหัสผ่าน ถ้า MediaMTX ใช้ค่าเริ่มต้น ใครในวงก็เปิด :8889 ดูได้
  • ถ้าจะให้ MediaMTX คุมกล้อง Arducam เอง คู่มือ MediaMTX เตือนว่าอาจต้องคอมไพล์ใหม่กับ libcamera ของ Arducam และจะเสีย picamera2 (ซูม/โฟกัส/ภาพนิ่ง)

ค. robot-update

ข้อดี

  • สองสตรีมจาก ISP: ภาพสดเล็ก ถ่ายจาก main ได้โดยภาพสดไม่หยุด
  • AI แนะนำเลขมิเตอร์ (ONNX ผ่าน OpenCV) ตั้งเกณฑ์ไว้ที่ 0.6 ทดสอบกับรูปจริง 104 ครั้ง แนะนำ 81 ครั้งและถูกทุกครั้ง
  • ขั้นตอนบันทึกค่าดีมาก มีค่าครั้งก่อน เตือนมิเตอร์วนรอบ และ outbox SQLite กันส่งซ้ำด้วย UUID
  • โค้ดเล็ก แยกไฟล์ดี มี unit test ทั้ง Python และ JS

ข้อเสีย

  • ภาพสดเล็ก (กว้าง 480) และรอรอบไปกลับทุกใบ ไกลแล้ว fps ตก
  • ภาพถ่าย 1280×960 เท่านั้น ห่างจาก 64MP มาก ซูมได้แค่ 2× ด้วย CSS
  • โปรโตคอล ESP32 คนละแบบ ไม่มีความเร็วอนาล็อก แขน pan หรือจอย
  • ไม่มีรหัสผ่าน ใช้ได้แค่ในวงเดียวกัน ส่งต่อผ่าน hub ไม่ได้ถ้าไม่เขียนเพิ่ม

ถ้าเลือกแต่ละทาง ต้องทำอะไร และเสียอะไร

ทางที่ 1 · ระบบเดิม + WebRTC แนะนำ

ต้องทำ

  1. วาง server.py (md5 fa0d4a93…), setup_webrtc.sh, mediamtx.yml, mediamtx.service ลงใน /home/pi/server/
  2. รัน bash setup_webrtc.sh บน Pi (ลง python3-av + MediaMTX v1.9.3 + service)
  3. ถ้าสคริปต์บอกว่า picamera2 ยังไม่มี PyavOutput ให้ส่งเลขรุ่นมาดูก่อน ห้ามอัปเกรดเอง เพราะอาจทำให้กล้อง Arducam ใช้ไม่ได้
  4. เปิดหน้าคุมหุ่น แถว "ภาพสดวิ่งทาง" ต้องขึ้น WebRTC (วิดีโอ H.264)
  5. ขับออกไปไกลแบบที่เคยค้าง ถ้ายังสะดุด ลด --h264-kbps 1000

เสีย / ต้องรู้

  • ใช้ซีพียูเพิ่มสำหรับ H.264 เอกสาร Raspberry Pi วัดโหมดหน่วงต่ำที่ 1080p30 ได้ 62–90% ของหนึ่งคอร์ ที่ 720p25 ใช้พิกเซลต่อวินาทีราว 37% ของนั้น จึงประมาณได้ราว 23–33% ของหนึ่งคอร์ (ประมาณจากสัดส่วน ไม่ได้วัดบนหุ่น)
  • เพิ่ม service MediaMTX และพอร์ต UDP/TCP 8189
  • คนเข้าผ่าน Funnel ได้แค่ JPEG สำรอง (UDP ผ่าน Funnel ไม่ได้)
  • ไม่เสียความสามารถเดิมเลย ถ้ามีปัญหาปิด MediaMTX แล้วกลับไปใช้ JPEG ได้ทันที

ทางที่ 2 · ย้ายไป robot-update ทั้งระบบ ไม่แนะนำ

ต้องทำ

  1. แฟลช ESP32 ใหม่ให้รับ JSON ของ robot-update หรือเขียนตัวแปลงเป็น #M/#S
  2. เพิ่มแขน pan ความเร็วอนาล็อก จอย แปรงหลายระดับ เข้าไปในโปรโตคอลและหน้าเว็บ
  3. เพิ่มรหัสผ่าน และทำให้ WebSocket 8765 ผ่าน hub/Funnel ได้
  4. ต่อ outbox เข้ากับ hub ของเรา (API คนละแบบ)
  5. ปิด camera-streamer ของ Arducam (setup_pi.sh ของเขาทำให้)

เสีย

  • ภาพนิ่ง 64MP เหลือ 1280×960 (เล็กลงราว 50 เท่า)
  • ซูมที่เซนเซอร์ 8× โฟกัสมือ และสแกนโฟกัส
  • เว็บลูกบ้าน/เจ้าของหอ เชื่อมกับหุ่นต้องทำใหม่
  • ปัญหาหุ่นไกลแล้วค้างก็ยังอยู่ เพราะเป็น TCP ขอทีละใบเหมือนเดิม แค่ภาพเล็กลง

ทางที่ 3 · ย้ายไป raspberry_pi ทั้งระบบ ไม่แนะนำ

ต้องทำ

  1. เปลี่ยนแหล่งภาพจากเว็บแคมเป็นกล้อง CSI: ให้ MediaMTX คุมกล้องเอง (rpiCamera ซึ่งอาจต้องคอมไพล์ใหม่กับ libcamera ของ Arducam) หรือเขียนตัวส่งจาก picamera2 ซึ่งก็คือทางที่ 1
  2. เขียนระบบขับหุ่นผ่านเว็บใหม่ทั้งหมด (ในโค้ดไม่มี)
  3. ใส่รหัสผ่าน และปิด :8889 ไม่ให้ใครก็ดูได้
  4. เลือกระหว่าง Google Drive/Sheets กับ hub

เสีย

  • ภาพนิ่ง 64MP ซูม และโฟกัส ถ้าให้ MediaMTX คุมกล้อง (picamera2 เปิดกล้องตัวเดียวกันพร้อมกันไม่ได้)
  • การขับ จอย แขน และระบบหยุดเองฝั่ง Pi
  • ได้แค่ข้อดีเรื่อง WebRTC ซึ่งทางที่ 1 ได้มาแล้วโดยไม่เสียอะไร

ของที่ควรยืมจาก robot-update ทีหลัง

  1. AI แนะนำเลขมิเตอร์ meter_ai/: ใช้ OpenCV + numpy อย่างเดียว ใส่ใน server.py ตอนถ่ายได้ แสดงเป็นค่าแนะนำให้คนกดยืนยัน ภายหลังย้ายไปรันบน Hailo-8L ได้
  2. ขั้นตอนบันทึกค่าหลังถ่าย: ชนิด → ห้อง → ค่า โชว์ค่าครั้งก่อน เตือนถ้าน้อยกว่าเดิม (มิเตอร์วนรอบ) ใช้กับกล่องติดป้ายห้องของเราได้ตรง ๆ
  3. ปุ่ม "ถ่ายเร็ว": ดึงภาพจากสตรีมหลักโดยไม่สลับโหมด ภาพสดไม่หยุด เก็บปุ่ม 64MP ไว้ใช้ตอนต้องการความชัดสูงสุด
  4. คุมได้คนเดียว + หน้าเดิมแย่งคืนได้ทันที (ControllerLock + ?client=) กันคนสองคนขับพร้อมกัน

สิ่งที่ต้องให้คุณทำหรืออนุญาต

รายงานนี้ทำในเครื่องทดสอบทั้งหมด ไม่ได้แตะ Pi โน้ตบุ๊ก หรือหุ่น ขั้นต่อไปที่ต้องทำบนเครื่องจริงและต้องให้คุณตัดสินใจมีดังนี้

งานสิทธิ์ที่ต้องใช้ความเสี่ยง
รัน setup_webrtc.shsudo บน Pi, ออกเน็ตไป GitHub และ aptต่ำ ปิด MediaMTX แล้วกลับเป็น JPEG ได้
อัปเกรด python3-picamera2sudo aptสูง อาจทำให้กล้อง Arducam ใช้ไม่ได้ ทำเมื่อจำเป็นเท่านั้น
เปิดพอร์ต 8189 (UDP/TCP)ไม่ต้องทำอะไร ถ้า Pi ไม่ได้เปิดไฟร์วอลล์ต่ำ เป็นท่อวิดีโอที่ต้องเจรจาผ่านรหัสก่อน
แก้ Funnel (เน็ต AIS ตัดสาย)หน้า admin ของ Tailscaleไม่กระทบหุ่น
แฟลช ESP32 (เฉพาะทางที่ 2)ถอด robot-server แล้วแฟลชสูง ไม่แนะนำ

ขีดจำกัดของรายงานนี้

  • ไม่ได้วัดบนหุ่นจริง ตัวเลขทั้งหมดมาจากเครื่องทดสอบ x86 และลิงก์จำลอง ส่วนค่าซีพียูบน Pi 5 ประมาณจากเอกสารของ Raspberry Pi
  • ความหน่วงของ WebRTC ตั้งแต่กล้องถึงจอยังไม่ได้วัด ทดสอบแค่ว่าวิดีโอขึ้น เดินต่อเนื่อง และสลับทางสำรองได้ (Chromium + MediaMTX จริง 10/10)
  • ส่วน MediaMTX ของ raspberry_pi อนุมานจากโค้ด เพราะไม่มีไฟล์ตั้งค่าใน zip
  • คลิปทดสอบเป็นภาพสังเคราะห์ที่มีลายผนังถี่กว่าของจริง ตัวเลขแบนด์วิดท์จึงเป็นกรณีหนัก แต่สัดส่วนระหว่างวิธีเชื่อถือได้
