## 2. ข้อสรุป

**ใช้ระบบของเราเป็นฐาน + เปิดวิดีโอ WebRTC (ทางที่ 1) — เขียนเสร็จแล้ว รอติดตั้งบนหุ่น**

เหตุผลสั้น ๆ
1. อาการ "หุ่นไกลแล้วภาพค้าง" มาจาก **JPEG ใช้เน็ตมาก + วิ่งบน TCP** (แพ็กเก็ตหาย = หยุดรอ) — ทางแก้คือวิดีโอ H.264 บน UDP แบบที่ raspberry_pi ใช้
2. raspberry_pi ให้ MediaMTX/ffmpeg คุมกล้อง → ถ้าลอกทั้งระบบเสียภาพนิ่ง 64MP ซูมที่เซนเซอร์ โฟกัส และไม่มีระบบขับผ่านเว็บเลย
3. robot-update ใช้ภาพสดแบบขอทีละใบ (กลไกเดียวกับ `/frame` ที่เราเลิกใช้แล้ว) ภาพเล็กมาก (กว้าง 480) คุยกับ ESP32 คนละโปรโตคอล ไม่มีรหัสผ่าน ถ้าย้ายต้องแฟลช ESP32 ใหม่และเสียภาพนิ่ง 64MP → เหลือ 1280×960
4. ทางที่ 1 ได้ข้อดีของ raspberry_pi มาโดยไม่เสียอะไร และถอยกลับเป็น JPEG ได้ทันทีถ้ามีปัญหา

ของดีจาก robot-update ที่ควรยืมทีหลัง: AI แนะนำเลขมิเตอร์ (`meter_ai/`, OpenCV ล้วน), ขั้นตอนบันทึก ชนิด→ห้อง→ค่า, ปุ่ม "ถ่ายเร็ว" จากสตรีมหลักไม่ต้องหยุดภาพ, ล็อกคนขับคนเดียว

## 4. หลักการทำงานของแต่ละระบบ (สรุปจากโค้ด)

### ก. ระบบเดิม (เช้า 15 ต.ค.)
- `picamera2` video config main 1280×720, กล้องตรึง 12 fps (`FrameDurationLimits` หัวท้ายเท่ากัน), บัฟเฟอร์ 2, NoiseReduction HighQuality, Sharpness 2.0
- `JpegEncoder(q=75)` เข้ารหัสด้วยซีพียูทุกเฟรม → `/stream` MJPEG ดันต่อเนื่อง (มี `SO_SNDBUF` + `select` ทิ้งเฟรม) → hub `pipe_mjpeg` ส่งต่อ
- คำสั่ง: เว็บยิง `GET /drive` ทุก 120 ms (`setInterval`), `/status` ทุก 250 ms → `DriveMux` 20 Hz รวมจอย (evdev) → `RobotLink` serial `#M,l,r` / `#S,pan,tilt` → ESP32 (หยุดล้อเองถ้าเงียบ 400 ms)
- ภาพนิ่ง: `switch_mode_and_capture_file` เต็มเซนเซอร์ (หุ่นรายงาน 9248×6944) ภาพสดหยุด 1–3 วิ → `~/robot_photos` → `push.py` ทุก 20 วิ → hub
- ซูม `ScalerCrop` ถึง 8× (คมราว 6×), AF กรอบกลาง + ปรับมือ + สแกน, Basic auth
- จุดอ่อน (แก้ไปแล้ววันนี้): ภาพสะสมในท่อ, Nagle หน่วง 44 ms/คำขอ, คำขอซ้อน, `/status` fork `vcgencmd` 4 ครั้ง/วิ

### ข. raspberry_pi
- กล้อง: เว็บแคม USB (คอมเมนต์ในโค้ดระบุ Logitech **Brio 4K**) OpenCV V4L2 MJPG 1280×720@30 อ่านในเธรด เก็บเฉพาะ JPEG ล่าสุด
- ภาพสด: หน้าเว็บเปิด `iframe` ไป `:8889/robot` = หน้า WebRTC ของ **MediaMTX** — **ไม่มีไฟล์ตั้งค่า MediaMTX ใน zip** ส่วนตัวแปลงเป็น H.264 อนุมานจาก (1) Brio ส่ง H.264 เองไม่ได้ (2) โค้ดรองรับ `CAMERA_RTSP_URL` (3) คู่มือ MediaMTX แนะนำ `ffmpeg -f v4l2 … libx264 -preset ultrafast -b:v 600k` สำหรับเว็บแคม
- ถ่ายรูป: `/capture?z=1..4` เอา JPEG ล่าสุด → ถอด → ครอปตรงกลางตามซูม → JPEG q90 → คิวอัปโหลด 1 งาน → Google Drive (ตั้งลิงก์ให้ใครก็เปิดได้) + Google Sheets
- ESP32: ส่ง `PI_CMD DRIVE l r` มาทาง serial หรือ TCP :8765 → Pi ตรวจรูปแบบแล้วตอบ `OK DRIVE` **ไม่ได้สั่งมอเตอร์** หน้าเว็บไม่มีปุ่มขับ
- ไม่มีรหัสผ่าน ไม่มีชุดทดสอบ

### ค. robot-update
- กล้อง: `picamera2` main 1280×960 RGB888 + lores 640×480 RGB888 (ISP ย่อ), กลับหัว, AF ต่อเนื่อง
- `FrameGrabber` เธรดเดียวอ่าน lores ทุกเฟรม (`capture_request` → `make_array` → `release`)
- ภาพสด: `/api/frame.jpg?after=N` ขอทีละใบ (รอเฟรมใหม่ ≤ 1.5 วิ) ย่อกว้าง 480 + `cv2.imencode` q70 **ต่อคำขอ** เพดาน 15 fps (มี `/video_feed` MJPEG ด้วยแต่หน้าเว็บไม่ใช้)
- ถ่ายรูป: `capture_hires` ดึง main 1280×960 เฟรมถัดไป ไม่หยุดภาพสด → JPEG q85 → AI ONNX (`cv2.dnn`, เกณฑ์ 0.6) → เก็บชั่วคราว → เลือกชนิด/ห้อง/ค่า → Outbox SQLite (UUID) → Cloud ทุก 5 วิ
- ขับ: `websockets` :8765 JSON `{move:{forward,backward,left,right}, tilt, blower}` ทุก 100 ms → `RobotBridge` (คุมได้คนเดียว, หยุดถ้าเงียบ 0.5 วิ, หน้าเดิมแย่งคืนได้) → serial JSON → ESP32 (เฟิร์มแวร์คนละแบบกับเรา)
- Flask :5000 ไม่มีรหัสผ่าน, มี pytest + node test, `setup_pi.sh` ปิด `camera-streamer` ของ Arducam

### ง. ที่แนะนำ (= server.py ปัจจุบัน `fa0d4a93…`)
- กล้องสองสตรีม: main 1280×720 YUV420 → `LibavH264Encoder` (ultrafast + zerolatency + baseline, 2 Mbit/s, ภาพหลักทุก 1 วิ) → `PyavOutput` RTSP → MediaMTX (ฟัง 127.0.0.1) → WebRTC UDP/TCP 8189
- lores 848×480 → JPEG q65 → `/ws` ดันใบล่าสุด หน้าต่างตอบรับ 2 (https 3) — ทางสำรอง + ใช้กับ Funnel
- `/whep` ผ่านรหัสก่อนส่งต่อ MediaMTX, คำสั่งขับวิ่งในสาย `/ws`, `--webrtc auto|on|off`, ถอยกลับ JPEG ทุกจุด
